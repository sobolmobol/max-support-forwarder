# MAX Support Forwarder

Двусторонний пересыльщик между личными диалогами аккаунта MAX и рабочей
беседой поддержки.

Это userbot на неофициальном внутреннем API MAX, а не бот официального Bot API.
На сервере должен работать только один экземпляр с одной session-базой.

## Что умеет

- Личные сообщения пересылаются в заданную рабочую беседу.
- Reply операторов пересылаются обратно в нужный личный диалог.
- Фото, обычные видео, кружки, голосовые сообщения, файлы, стикеры и другие
  вложения пересылаются нативным `forward_message` на стороне MAX.
- SQLite-outbox не теряет принятые задания при падении процесса или сети.
- После reconnect очередь продолжает доставку с экспоненциальной задержкой.
- PyMax 2.4 обновляет выданный сервером token и сам восстанавливает соединение.
- При отзыве token процесс не падает: он удаляет невалидную сессию и ждёт новый
  SMS-код в одноразовом файле.
- Логи ротируются.

## Как работает маршрутизация

1. Бот делает нативный forward личного сообщения в рабочий чат.
2. Следом отправляет reply-карточку с именем, ID и, если разрешено, телефоном.
3. ID обоих сообщений сохраняются в `cache/relay_state.db`.
4. Оператор отвечает reply на пересланное сообщение или карточку.
5. Ответ целиком пересылается в исходный личный диалог.

Сообщение оператора без reply намеренно игнорируется: получателя невозможно
определить однозначно.

## Установка на сервере

Требуется Python 3.10 или новее.

```bash
git clone https://github.com/sobolmobol/max-support-forwarder max-support-forwarder
cd max-support-forwarder
python -m venv .venv
./.venv/bin/python -m pip install --upgrade pip
./.venv/bin/python -m pip install .
cp .env.example .env
```

На Windows используйте `.venv\Scripts\python.exe` вместо `.venv/bin/python`.

Заполните `MAX_PHONE` и `MAX_TARGET_CHAT_ID`, затем запустите:

```bash
./.venv/bin/python run.py
```

## Авторизация и восстановление сессии

Session хранится в `cache/forwarder_bot.db`. Не удаляйте каталог `cache` при
обновлении кода и не запускайте две копии процесса с одной базой.

При первом входе или отзыве token в логе появится путь к файлу SMS-кода.
Запишите код одной строкой:

```bash
printf '%s' '123456' > cache/sms_code.txt
```

Бот прочитает и сразу удалит файл. Для 2FA аналогично используется
`cache/2fa_password.txt`; постоянный пароль можно передать через
`MAX_2FA_PASSWORD` в `.env`.

Полностью автоматическая повторная авторизация невозможна, если MAX потребовал
SMS/2FA: код должен предоставить владелец номера. Процесс при этом остаётся
запущенным и продолжит работу сразу после появления файла.

## Обновление существующей машины

1. Остановите старый процесс.
2. Сделайте резервную копию `.env` и каталога `cache`.
3. Обновите исходники через Git.
4. Создайте новое `.venv` и выполните `pip install .`.
5. Не заменяйте серверный `cache/forwarder_bot.db` локальной копией.
6. Запустите процесс и проверьте строку `MAX подключён` в логе.

Старый `cache/message_mappings.json` автоматически импортируется в новую
SQLite-базу маршрутизации.

## Эксплуатация

- Основной лог: `logs/bot.log`.
- Неудачные доставки сохраняются в таблице `relay_jobs`.
- По умолчанию `BOT_JOB_MAX_ATTEMPTS=0`: доставка повторяется без ограничения,
  а сообщение остаётся в SQLite, пока MAX или сеть недоступны. Положительное
  значение включает лимит попыток и статус `failed`.
- `BOT_MAPPING_RETENTION_DAYS` определяет, сколько дней работают старые reply.
- Для диагностики временно используйте `PYMAX_LOG_LEVEL=DEBUG`, затем верните
  `WARNING`.

Пример systemd unit находится в `deploy/max-support-forwarder.service.example`.
